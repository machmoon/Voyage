# App Store screenshot plan, Voyage 1.0

Six screenshots, in order. Reasoning for the ordering is in the launch package; this file is the
production spec.

## Producing them

Captions live in `AppStore/screenshots.json`, not in code. To build:

```bash
python3 scripts/make_app_store_screenshots.py --list   # readiness of all six slots
python3 scripts/make_app_store_screenshots.py          # write the ready ones
```

Output lands in `AppStore/screenshots/` at 1320x2868, ready to upload. Slots whose source
capture does not exist yet are reported and skipped, so the command can be re-run as the
screenshot tour grows. Requires only Pillow and the system SF fonts, both already present.

Each slot below names the `filter` token the config uses to bind it to a file in `QA/`.

**Before capturing anything, read "Capture order: do these in this sequence" at the end of this
file.** Three slots depend on code changes landing first, and capturing early produces a
screenshot of a version that no longer exists without warning you.

## Capture setup

**Know what each flag does before capturing.**

`-VoyageDemoFlight` has a real but *partial* bug. `completeLeg()` fires when
`legElapsed >= legDuration` and the flag clamps `legDuration` to 60 seconds, so the session does
complete and **the arrival flow, stamp, baggage claim and logbook are all reachable in about a
minute.** What is broken is the visual phase progression: `climbEnd` computes to 135 seconds,
past the end of the leg, so the window scene **stays in climb for the whole flight** and cruise,
descent and landing never render.

- **Use `-VoyageDemoFlight`** for the arrival side: landing flow, baggage claim, passport stamp,
  logbook. Fast and correct.
- **Use `-VoyageShortFlights`** for any window or map frame mid-flight. It is the only flag under
  which cruise, descent and landing actually render.
- **Never use `-VoyageDemoFlight` for in-flight window or map frames.** They will show a climb
  scene regardless of the clock.

`ScreenshotTourUITests` uses `-VoyageShortFlights`.

Device: **iPhone 17 Pro Max, 6.9 inch, 1320x2868.** This is the only size Apple now requires and
it downscales to the 6.5 inch slot automatically.

Pin the status bar before capturing so all six frames match:

```bash
xcrun simctl status_bar booted override --time 9:41 --batteryState charged \
  --batteryLevel 100 --cellularBars 4 --wifiBars 3
```

Tonight's run already shows `9:41`, so this is in place.

## Caption treatment

Every competitor screenshot inspected during research carried overlaid text; not one was a bare
UI capture. Use the app's own signatures rather than a generic template.

- Background `Theme.ink`. Headline in the kerned VOYAGE weight, top-aligned, device frame below.
- One accent (`#4E8CFF`) per frame at most. Monospaced treatment for any airport code in a caption.
- Headline plus one supporting line. No emoji. No gradient mesh. No exclamation marks.

  header, "Where are we flying today?" and the route cards (`LAX Los Angeles → 1h 25m`,
  `YVR Vancouver → 2h 20m`).
- **Headline:** The route sets the timer.
- **Support:** SFO to LAX is 1h 25m because that is what the flight takes.
- **Status:** capturable now.

### 2. The boarding pass, mid-tear

- **Capture:** `qa-04-boarding-pass-pre-tear` (filter `qa-04-boarding-pass`), but pulled **partially torn** so the interaction
  reads as an interaction. Must show `VOYAGE AIR` / `VOY 424`, `SFO` to `LAX`, `FOCUS 1h 25m`,
  and the seat.
- **Headline:** Tear the pass to start.
- **Support:** Not a button. A decision.
- **Status: BLOCKED on a string, not on the capture.** The composite is correct and the built

  screenshot it advertises a capability the app does not have, which is a submission risk on a
  build that already carries two rejections. **Re-capture after the string changes.** Options
  and a recommendation are below. Note the interaction copy is now "Slide across the tear line to
  board", not "pull the stub down"; do not write a caption that describes the old gesture.

### 3. The window at cruise

  flight strip reads `VOY 424` and not a real carrier code before shipping.
- **Headline:** This is the screen you study next to.

## App preview video, partially blocked

Intended cut, 15 to 30 seconds: globe spin to LAX card (3s), seat tap (2s), pass tear with the
haptic beat visible (3s), window at climb (4s), landing and stamp (4s). No voiceover, no
licensed music, cabin ambience only.

The first three beats can be shot now under either flag, and the **stamp** beat can be shot now
under `-VoyageDemoFlight`, which reaches arrival in about a minute. What cannot be shot quickly
is any window or map view at **cruise, descent or landing**, because the demo flag renders only
climb. Those need `-VoyageShortFlights` and a real 1h 25m route, or the phase-schedule fix.


## Blocking copy defect on slot 2

`Voyage/Views/Boarding/BoardingPassView.swift:117` renders:

> Airplane Mode on. Nothing interrupts this flight.

That is written as a statement of fact about device state. The app neither sets Airplane Mode
nor observes it, and the comment at `BoardingPassView.swift:110` concedes the point: "iOS can't
flip Airplane Mode for you". The line needs to become an instruction or a rationale.

This is the owner's call, not an agent's, and `BoardingPassView.swift` carries uncommitted work
so no agent may edit it.

### Options

**A. Minimal edit, keeps the rhythm.**

> Turn on Airplane Mode. Nothing interrupts this flight.

One word changed. The second sentence, which is the part that carries the feeling, survives
untouched. Converts the false assertion into an instruction and stays true, because if the
traveler does it, nothing does interrupt the flight.

**B. Ties the instruction to the ritual moment.**

> Turn on Airplane Mode before you tear the pass.

Slightly stronger as an instruction because it names the deadline, and it sits directly above
the tear control. Loses the second sentence.

**C. Rationale rather than instruction.**

> Airplane Mode is the point. Nothing gets through for the next hour.

More voice, and it explains why rather than issuing an order. Weaker on a first run, because a
traveler who has not yet done it is told a philosophy instead of an action. The duration is also
a claim that varies by route.

### Recommendation

**Option A.** It is a one-word change, it preserves the cadence the owner clearly wrote for, it
keeps the pill the same width so the layout does not need revisiting, and it is unambiguously
true. B is the better instruction in isolation but gives up the line worth keeping. C reads well
and answers a question nobody is asking at that moment.

Whichever is chosen, re-run the tour and re-composite slot 2 before submission.


## Capture order: do these in this sequence

Several dependencies now interact, and three of them are invisible if you work from the
readiness table alone. **Apply the code changes first, then capture.** Capturing before a change
produces a screenshot of a version that no longer exists, and nothing warns you.

### Step 1. Land the code changes that alter a captured screen

| Change | Affects | Who |
| --- | --- | --- |
| `BoardingPassView.swift:117`, the Airplane Mode string | Slot 2 | Owner. See the copy options below |
| `voyage-design-owner-fixes.patch`, the `DivertedView.swift` hunk | Slot 4 | Owner |
| Launch-crash fix | The tour running at all | Engineering |
| Demo-flag phase schedule, optional | Nothing in this set. Only the video work | Engineering |

**The design patch changes slot 4 in three visible ways, not one.** Verified against the patch
at `out/voyage-design-owner-fixes.patch`:

1. The body sentence is rewritten, from "The app was in the background for over 30 seconds, so
   the flight put down at the nearest field. Your completed miles are still logged." to "Voyage
   ended the flight at 30 seconds in the background. The miles you already flew are logged."
2. **`stat("Status", "Incomplete")` is deleted**, so the stat row goes from three columns to two.
3. `Miles earned` becomes `Miles flown`.

The current `qa-12-divert-alert.png` shows the old three-column row with `STATUS Incomplete` and
`MILES EARNED`. After the patch that frame is wrong in three places.

**And the patch breaks the tour, which is worth knowing before 9am.**
`ScreenshotTourUITests.swift` asserts twice on copy the patch changes:

- `:475-476` matches on `"in the background for over 30 seconds"`, a phrase the new sentence
  does not contain.
- `:481` requires `app.staticTexts["Incomplete"]`, which the patch deletes.

Both fail once the patch lands. That is a **loud** failure rather than a silent stale capture,
which is the better outcome, but it means **the patch and the test update have to go in the same
commit** or the tour stops producing captures at all. The title assertion at `:465`,
"Flight diverted", is untouched and survives.

### Step 2. Normalise the status bar

**4:32**, `qa-01` and `qa-04` at **9:41**. Three clocks in one uploaded set reads as screen grabs
rather than a designed set. Before any capture run:

```bash
xcrun simctl status_bar booted override --time 9:41 --batteryState charged \
  --batteryLevel 100 --cellularBars 4 --wifiBars 3
```
